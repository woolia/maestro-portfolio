하나의 AI 창에서 모든 작업을 하면
왜 망가지는가

일반 AI 채팅 도구로 복잡한 프로젝트를 진행하면 두 가지 문제가 반복됩니다.

첫째, 컨텍스트 오염. PM 지시, 개발 코드, QA 결과가 하나의 긴 대화에 섞이면 AI는 앞 내용을 잊거나 엉뚱한 이전 맥락을 가져옵니다.

둘째, 책임 없는 협업. "누가 무엇을 했고 왜 그 결정을 했는지"가 기록되지 않으면 다음 작업에서 처음부터 다시 파악해야 합니다.

LangChain·AutoGen 같은 프레임워크는 코드로 파이프라인을 짜야 해서 새 프로젝트마다 오케스트레이션 코드를 다시 작성합니다.

Maestro는 이 두 문제를 역할 분리(자리) + 구조화 메시지(큐) + 파일 격리(샌드박스)로 풉니다.

⚠

컨텍스트 오염

PM 지시·코드·QA 결과가 하나의 대화에 섞여 AI가 이전 맥락을 잃거나 오용합니다.

⚠

책임 없는 협업

누가 무엇을 왜 결정했는지 기록이 없어 다음 작업에서 매번 처음부터 재파악합니다.

AI 팀 운영에 필요한 모든 것을 직접 설계했습니다

🪑

자리(Seat)

역할별 에이전트 슬롯

PM · Ace · 연구자 · 기획자 · 개발자 · QA · DevOps · 비서. 각 자리는 독립 세션 — 컨텍스트 오염 없이 역할에만 집중합니다.

자리역할
PM작업 배분·진행 관리 전담
Ace사용자와 직접 대화하는 대표 창구
researcher조사·분석 전문
spec-writer기획서·요구사항 작성
uiuxUI/UX 디자인
lead-developer아키텍처·리드 개발
developer구현
qa테스트·검증
devops인프라·배포
assistant조직 알림·팀 구성 제안
📋

작업 큐(Queue)

에이전트 간 구조화 협업

에이전트끼리 채팅하지 않습니다. PM이 큐로 작업 카드를 보내고, 자리는 착수·완료·막힘을 큐에 기록합니다. 근거·가정·미확인 사항이 항상 남습니다.

  • queue_assign — PM이 특정 자리에 작업 카드 생성
  • queue_update — in_progress / done / blocked 전환
  • queue_withdraw — 진행 중인 작업 즉시 회수
  • queue_list — 팀 작업 목록 조회
🗂

파일 샌드박스

자리별 쓰기 격리

각 자리는 자기 폴더(_seats/<자리>/)에만 쓸 수 있습니다. 다른 자리 파일은 읽기·복사만 가능 — 수정·삭제는 앱이 거부합니다. 동시 수정 충돌을 구조적으로 차단합니다.

📖

플레이북(Playbook)

반복 작업의 표준화

Ace가 샘플 작업을 완성하면 재현 가능한 절차를 문서화합니다. PM이 플레이북을 읽고 여러 자리에 배분하면 같은 품질로 반복 실행됩니다.

포함: 요청 원문 · 확정 결정 · 샘플 경로 · 절차·스크립트 · 가변 값 · 검수 체크리스트

💾

기억·로깅

세션을 넘나드는 컨텍스트

모든 메시지·도구 호출·결과가 JSONL로 기록됩니다. 세션이 새로 시작돼도 지난 결정·이슈를 검색할 수 있습니다.

기록 필드: id · seatId · at · kind · text

왜 프레임워크를 안 쓰고 직접 만들었는가

설계 결정

결정 1

큐 기반 협업 (채팅 대신 카드)

에이전트 간 자유 채팅 대신 구조화된 작업 카드를 선택했습니다.

이유

  • 채팅은 기록이 아니다 — 누가 언제 무엇을 결정했는지 추적 불가
  • 작업 상태(in_progress / done / blocked)를 강제하면 진행 상황이 항상 명확
  • 에이전트가 "기다리겠다고 말하고 턴을 끝내는" 패턴을 구조적으로 차단
결정 2

blocked_kind 7분류

막힘 상태를 단순 실패가 아닌 7가지 원인으로 분류합니다:

  • input_missing
  • permission
  • tool_missing
  • dependency
  • premise
  • question
  • external

이유

  • 원인마다 해결 주체가 다르다 (사람 vs. 다른 에이전트 vs. 대기)
  • dependency는 depends_on으로 대기 작업 ID 명시 — 해결되면 자동 재개
  • cause 이름으로 같은 원인을 묶어 한 번에 해결
결정 3

파일 샌드박스

공유 파일 시스템에서 여러 에이전트가 동시에 작업하면 충돌이 발생합니다. 자리별 쓰기 경로를 앱 레벨에서 강제 격리해 구조적으로 차단했습니다.

부작용

  • 협업을 위해 파일을 복사해야 하는 불편이 있지만,
  • 충돌 디버깅보다 훨씬 비용이 낮다고 판단했습니다.

이슈와 해결

[A] 작업 회수 불가

상황 — PM이 배분한 작업을 사용자가 취소하려 했으나 도구가 없었음

해결 — queue_withdraw 도구 추가. PM 규범에 "멈춰·중단" 신호 수신 시 열린 작업 전부 회수 명시

[B] 세션 만료 후 맥락 유실

상황 — 작업 완료 후 세션 초기화 → 다음 작업에서 이전 결정을 처음부터 재파악

해결 — done result 필수 항목화(바꾼 파일·실행한 확인·가정·미확인). 앱이 RESULTS.md에 자동 기록

[C] 에이전트 파일 충돌 가능성

상황 — 여러 자리가 동일 파일을 동시 수정할 경우 충돌 우려

해결 — 파일 샌드박스 + PM 배분 순서 조율 규범. 같은 파일을 두 자리가 동시 수정하지 않도록 강제

[D] AI 허위 사실 생성 (Hallucination)

상황 — 연구자·기획자가 자료 없이 수치·사례를 만들어낼 위험

해결 — 전 자리 공통 규범: 자료 없는 사실은 "[확인 필요: …]"로 표시, 임의로 채우지 않음
